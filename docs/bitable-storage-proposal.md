# 飞书多维表格存储方案提案

> 状态：设计提案，尚未实现。当前版本仍以 PostgreSQL 作为唯一账本存储，现有配置和部署方式不变。

## 摘要

LarkLedger 当前要求部署者准备 PostgreSQL。这个选择提供了事务、唯一约束、聚合查询和明确的数据所有权，适合长期运行；但对只想搭建个人记账机器人的用户而言，数据库往往比机器人本身更难部署。许多潜在用户没有 NAS、长期在线的电脑或现成的云数据库，也不熟悉数据库账号、迁移和备份。

本提案建议保留 PostgreSQL，同时增加飞书多维表格存储后端：

- 个人、低频和体验型部署可以优先选择多维表格，直接在飞书中查看自己的账目，不再单独维护 PostgreSQL。
- 小团队可以在明确权限边界和数据规模的前提下使用多维表格。
- 对可靠性、查询性能、数据量或审计能力要求较高的部署继续使用 PostgreSQL。

多维表格模式减少的是**数据库运维**，不是全部部署工作。机器人程序仍需运行在一台可持续联网的设备或托管平台上，也仍可能使用第三方 AI、视觉、语音和汇率服务。本提案中的“免费选择”不承诺飞书套餐、运行平台或第三方服务永久免费。

## 为什么需要第二种存储后端

当前数据流为：

```text
飞书消息 → 事件去重 → AI 结构化解析 → LedgerService → PostgreSQL → 飞书回复
```

账目、分类预算、预算提醒和已处理事件分别保存在 PostgreSQL 表中。所有业务操作都按飞书用户 `open_id` 隔离，并依赖数据库事务、唯一约束和固定 SQLAlchemy 查询保证一致性。详细现状见[架构说明](architecture.md)。

这套架构的主要障碍不是数据库授权费用，而是使用成本：部署者需要获得一个应用可访问的 PostgreSQL、执行迁移、管理连接凭据、监控容量并安排备份。即使数据库软件免费，这些步骤仍会劝退没有服务器经验的用户。

多维表格已经位于飞书工作流中，记录可被直接浏览、筛选和导出。将它作为可选账本后端，可以让开源用户用自己租户内的资源保存数据，而不是依赖项目方运营一个集中式云服务。

## 飞书开放平台提供的能力

飞书将多维表格中的每一行表示为一条 `record`，字段值放在 `fields` 中。开放平台提供数据表、字段、记录、视图和权限等 API；记录支持新增、检索、更新、删除及批量操作。调用时需要访问凭证、代表多维表格的 `app_token` 和代表数据表的 `table_id`。

与本提案直接相关的官方能力如下：

- [多维表格概述](https://open.feishu.cn/document/server-docs/docs/bitable-v1/bitable-overview?lang=zh-CN)列出了数据表、记录、字段、视图和权限接口。
- [新增记录](https://open.feishu.cn/document/server-docs/docs/bitable-v1/app-table-record/create?lang=zh-CN)要求调用身份拥有相应编辑权限，文档标注的接口频率限制为 50 次/秒。
- [查询记录](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/bitable-v1/app-table-record/search)支持筛选、排序和分页，单次最多查询 500 行，文档标注的接口频率限制为 20 次/秒。
- [多维表格记录数据结构](https://open.feishu.cn/document/docs/bitable-v1/app-table-record/bitable-record-data-structure-overview?lang=zh-CN)说明了文本、数字、日期、人员等字段的传输结构。
- [批量更新记录](https://open.feishu.cn/document/server-docs/docs/bitable-v1/app-table-record/batch_update?lang=zh-CN)可用于迁移和维护任务，单次最多更新 1,000 条记录。

以上是官方接口事实。以下限制属于基于当前 API 形态作出的工程判断：多维表格 API 没有提供与 PostgreSQL 等价的跨表事务、数据库唯一约束和任意 SQL 聚合能力；单个数据表的写入还需要控制并发和重试。因此它适合个人及轻量协作数据，但不能被当成关系数据库的无差别替代品。

## 方案对比

| 维度 | 飞书多维表格 | PostgreSQL |
| --- | --- | --- |
| 初次部署 | 无需安装数据库；需要创建多维表格、字段并授权应用 | 需要数据库实例、账号、连接串和迁移 |
| 日常查看 | 可直接在飞书中筛选、排序和编辑 | 通常需要管理工具或额外界面 |
| 数据读写 | 依赖飞书网络、凭证、权限和 API 配额 | 依赖数据库网络和自身资源 |
| 查询与报告 | 筛选后分页读取，由应用完成聚合 | 数据库可直接完成筛选、排序和聚合 |
| 事务与幂等 | 需要应用层补偿、串行化和幂等键设计 | 可使用事务、唯一约束和行锁 |
| Schema 稳定性 | 表格拥有者可能在界面中误改字段 | 由迁移脚本受控管理 |
| 可视化 | 内置视图、筛选和仪表盘能力 | 需要另接工具或由项目生成报告 |
| 备份与迁移 | 可人工导出；自动备份需额外实现 | 备份、恢复和复制工具成熟 |
| 扩展性 | 适合个人和低频、小规模团队 | 更适合较大数据量、并发和复杂查询 |
| 数据所有权 | 保存于部署者自己的飞书租户 | 保存于部署者自己的数据库 |

多维表格是否“免费”取决于部署者的飞书版本、数据规模和当时的开放平台规则。项目文档只应承诺“不需要单独维护 PostgreSQL”，不应承诺无限记录、无限 API 调用或永久免费托管。

## 推荐产品形态

### 一次部署只选择一个事实来源

建议增加统一的存储接口，让消息接入、AI 解析、业务规则和回复逻辑不感知具体存储：

```text
MessageProcessor
      ↓
LedgerService
      ↓
LedgerRepository
      ├── PostgresLedgerRepository
      └── BitableLedgerRepository
```

每个部署实例只能选择一个主后端。PostgreSQL 和多维表格不能同时接受账目修改，也不提供持续双向同步。这样可以避免重复记录、修改覆盖、删除状态冲突和预算统计口径不一致。

存储接口至少要覆盖：领取事件、新增单笔或批量账目、读取和修改最近一笔、软删除、按条件汇总、生成报告数据，以及分类预算和提醒阈值管理。业务层继续负责金额、时间、币种、批量上限和 `open_id` 隔离，AI 仍然不能直接访问任何存储连接或生成查询表达式。

### 建议的数据表

一个部署实例使用一个由部署者控制的多维表格 App，其中包含四个数据表：

| 数据表 | 建议字段 | 关键用途 |
| --- | --- | --- |
| 账目 | 记录 ID、用户 Open ID、金额、币种、方向、分类、备注、发生时间、来源类型、来源消息 ID、来源项序号、创建时间、更新时间、删除时间 | 保存收支和软删除状态；来源消息 ID 与项序号组成应用级幂等键 |
| 分类预算 | 预算 ID、用户 Open ID、分类、金额、创建时间、更新时间 | 保证每个用户每个分类只有一个有效预算 |
| 预算提醒 | 提醒 ID、预算 ID、月份、阈值、提醒时间 | 避免同一自然月重复发送 80% 或 100% 提醒 |
| 已处理事件 | 事件 ID、处理状态、处理时间、失败阶段、重试次数 | 对飞书事件去重，并为可控重试保留状态 |

字段的显示名称可以使用中文，但程序不应只依赖可被用户随意修改的显示名称。初始化或健康检查需要列出字段并验证类型；缺列、重名或类型不符时停止写入并返回明确错误，避免把错误数据写入错误列。

### 配置提案

未来实现可考虑增加以下环境变量；名称和必填规则应在开发阶段通过配置评审后确定：

```dotenv
LARK_LEDGER_STORAGE_BACKEND=bitable
LARK_LEDGER_BITABLE_APP_TOKEN=replace-me
LARK_LEDGER_BITABLE_ENTRIES_TABLE_ID=tblxxxxxxxx
LARK_LEDGER_BITABLE_BUDGETS_TABLE_ID=tblxxxxxxxx
LARK_LEDGER_BITABLE_BUDGET_ALERTS_TABLE_ID=tblxxxxxxxx
LARK_LEDGER_BITABLE_PROCESSED_EVENTS_TABLE_ID=tblxxxxxxxx
```

这些变量目前只是接口草案。本提案不修改 `config.py`、`.env.example` 或现有 PostgreSQL 默认值，也不表示当前版本已经支持这些配置。

## 一致性、幂等和故障处理

多维表格模式不能照搬 PostgreSQL 的事务语义，需要显式定义较弱但可预测的行为：

1. 用 `event_id` 查询“已处理事件”，领取成功后记录处理状态；相同事件再次投递时不重复执行。
2. 新增账目时同时保存 `source_message_id` 和 `source_item_index`，重试前先查询幂等键。
3. 对同一用户的修改、撤销和预算更新在应用层串行执行，避免“最近一笔”在并发请求中发生变化。
4. 批量记账逐项写入并记录结果；发生部分失败时，不宣称整批成功，而是返回可重试项和错误编号。
5. 对限流、超时和临时服务错误使用有上限的指数退避；权限错误、字段缺失和参数错误不自动重试。
6. 汇总和报告必须完整处理分页，并在应用内完成 Decimal 金额聚合，不能使用浮点数累加。

上述设计可以降低重复记账概率，但在多维表格不提供等价事务和唯一约束的前提下，无法承诺与 PostgreSQL 完全相同的强一致性。报告和用户手册必须如实说明这一点。

## 权限、隐私和安全边界

多维表格模式不应建设由项目方集中托管所有用户账本的公共服务。每位部署者应在自己的飞书租户中创建或授权多维表格，并自行控制应用凭据和协作者。

- 应用只申请读取和编辑指定多维表格所需的最小权限；不因方便而申请无关通讯录或云文档权限。
- 默认不把含有多人账目的底表共享给普通机器人用户。机器人在代码中按 `open_id` 过滤，并不能阻止拥有底表查看权限的人在飞书界面看到其他记录。
- 如果部署者需要让用户直接浏览表格，必须使用经过验证的高级权限或为不同用户提供物理隔离；在验证前，不能把多人共享底表描述为安全能力。
- 日志不得记录 `app_token`、访问凭证、消息正文、账目备注或完整 API 响应；错误回复只包含可定位的错误编号。
- 表格管理员手工修改金额、用户标识或删除状态会绕过机器人业务校验。个人部署可以把这种能力视为人工纠错入口，多人部署则应限制编辑权限并保留审计流程。

## 迁移与回退

首个迁移工具只支持 **PostgreSQL → 多维表格** 单向导出，不做实时同步：

1. 在目标多维表格中创建并校验固定 Schema。
2. 按稳定顺序分页读取 PostgreSQL，保留原记录 ID 和来源幂等键。
3. 分批写入多维表格，记录批次、成功项和失败项，使任务可以续跑。
4. 对数量、金额合计、用户分布、预算和提醒记录做迁移后校验。
5. 完成校验后由部署者切换存储配置；原 PostgreSQL 保持只读观察一段时间，不执行双写。

从多维表格回迁 PostgreSQL 也应作为后续独立工具设计。任何迁移都必须先备份源数据，并在维护窗口内停止机器人写入。不能通过复制环境变量在运行中无缝切换事实来源。

## 分阶段实施路线

1. **抽象存储边界**：为账目、预算、提醒和事件幂等定义 Repository 接口，用 PostgreSQL 实现回归全部现有行为。
2. **实现多维表格基础读写**：完成鉴权、Schema 验证、分页、筛选、CRUD、重试、限流和可诊断错误。
3. **补齐业务语义**：实现批量记账、最近一笔、软删除、预算阈值、汇总、报告和并发控制，并建立与 PostgreSQL 共用的契约测试。
4. **提供单向迁移工具**：实现 PostgreSQL 到多维表格的可恢复导出和一致性校验，提供备份与回退说明。
5. **小范围验证再调整推荐项**：先标记为实验性后端；在真实个人账本上验证稳定性、权限和 API 配额后，再决定新部署是否优先推荐多维表格。

每一阶段都应保持 PostgreSQL 用户可以原地升级，不要求迁移，也不能改变现有账本数据。

## 用户选择指南

| 使用场景 | 推荐后端 | 原因 |
| --- | --- | --- |
| 个人体验、低频记账、没有数据库 | 多维表格 | 部署门槛低，数据可在飞书中直接查看 |
| 家庭或小团队、低并发且管理员统一管理底表 | 多维表格（审慎） | 协作方便，但必须先解决底表权限和人工编辑边界 |
| 已有 NAS 或长期在线服务器 | PostgreSQL | 数据库可与应用一同自托管，可靠性和备份更可控 |
| 较多用户、较大数据量、频繁报告 | PostgreSQL | 聚合查询、事务、唯一约束和扩展能力更合适 |
| 对审计、恢复和强一致性要求较高 | PostgreSQL | 数据库工具链和故障恢复路径更成熟 |

出现以下任一情况时，应优先使用或迁移到 PostgreSQL：多维表格查询分页已经明显影响响应时间；频繁触发限流或超时；需要跨记录原子操作；多人需要直接访问底表但无法可靠隔离；需要复杂分析、自动备份、时间点恢复或更严格的审计。

## 验收标准

多维表格后端只有同时满足以下条件，才能从“实验性”提升为普通可选项：

- 现有单笔、批量、修改、撤销、预算、汇总和报告契约测试在两个后端上得到一致业务结果。
- 重复 `event_id` 和重复消息不会在正常重试路径中新增重复账目。
- 查询和报告正确处理超过 500 行的分页数据。
- 权限撤销、字段误改、限流、超时和部分写入均有安全失败与明确恢复说明。
- 文档能让新用户在不接触 PostgreSQL 的情况下完成多维表格初始化、授权、备份和故障排查。
- PostgreSQL 用户升级后行为、配置和数据均保持兼容。

## 结论

多维表格不能替代 PostgreSQL 的全部数据库能力，但它能解决开源项目最现实的采用障碍之一：让没有 NAS、数据库或运维经验的用户，也能用自己已有的飞书环境保存账本。

因此，LarkLedger 适合采用“双后端、单事实来源”的长期方向：多维表格服务于低门槛和可视化，PostgreSQL 服务于可靠性和扩展性。先以实验性可选后端交付、验证真实限制，再决定是否把它作为个人新部署的优先推荐，既能增加免费的选择，也不会牺牲现有用户的数据安全和升级路径。
